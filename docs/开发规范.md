# QC-quicklog 开发规范

> 本文件是项目**强制约束**，任何版本迭代（新增序号、改解析器、改分类、改导出）都必须遵守。
> 制定背景见 [V7.7 事故复盘](#附事故复盘v77-序号29)，起因是 V7.6「看似稳定」却在遇到新数据变体时一次性暴露两个潜伏 bug。

---

## 三条铁律（不可绕过）

### 铁律一：新 JSON 必须过回归测试，不许直接导入

**规则**：任何新增序号的 JSON 到货后，**先跑回归测试，确认全绿，才允许合入和交付使用**。

```bash
node test_v74_json.js
```

**验收标准**（三条都满足才算过）：
1. **条数正确** —— 解析出的记录数 == JSON 页数（或人工点数），不允许少一条
2. **关键字段无空** —— 规格型号、炉号/批号、证书出厂编号、材质、数量
3. **分类正确** —— 按下方[业务分类定义](#业务分类定义固定不可改)核对

**新增序号 = 新增测试断言**。新序号 JSON 放进 `tests/fixtures/`，并在 `test_v74_json.js` 里补上预期值，让下次改动能自动拦住回归。

> 反面案例：序号29 的 11 页 JSON 未经测试直接交付，结果漏 1 条 + 5 条字段错位。

---

### 铁律二：解析器检测条件禁止使用「前 N 行」假设

**规则**：解析器判断"这张表是不是我的格式"时，**禁止**用 `table.slice(0, N)` 之类的行号假设。**必须全表扫描**。

```javascript
// ❌ 错误：假设特征词一定在前 5 行
var rowStr = table.slice(0, 5).map(function(r) { return r.join('|'); }).join('|');

// ✅ 正确：全表扫描，不依赖行号
var rowStr = table.map(function(r) { return r.join('|'); }).join('|');
```

**取字段同理**：用 `kvLookup(table, keyPattern)` **整表按 key 定位**，不要按固定行号/列号硬取值。

**原因**：同一厂家不同批次、不同 OCR 结果的表格会多出"收货单位"等首行，把特征词挤出前 N 行 → 检测失败 → 该页落入通用解析器 → 字段全乱。

> 反面案例：`parseHengtongCert` 用 `slice(0,5)` 找"供货状态"，序号26 恰好通过，序号29 因首行多了"收货单位"而检测失败，漏掉 1 整条。

---

### 铁律三：分类规则按业务定义固化，改动需三处同步

**规则**：物资分类以业务定义为准，**不许为了"匹配上"而放宽正则**。

新增或修改物资类型时，**三处必须同步更新**，缺一不可：

| # | 位置 | 说明 |
|---|---|---|
| 1 | `rules/8.28-V7.4规则更新.xlsx` | 规则表，业务口径的唯一来源 |
| 2 | `classifyProduct()`（HTML 内） | 代码实现，必须与规则表一致 |
| 3 | `test_v74_json.js` | 测试断言，钉死预期分类 |

> 反面案例：`classifyProduct` 把"无缝"放进管材识别词，遇到"无缝弯头90°"就误判成管材——**"无缝"是工艺描述，不是品类**，用它做分类依据从根上就错了。

## 业务分类定义（固定，不可改）

用户确认的口径：

| 分类 | 定义 | 识别词 |
|---|---|---|
| **管材** | 钢管类别 | 钢管 / 焊管 / 流体输送 |
| **管件** | **三通、弯头、大小头、管帽、异径管等配件** | 弯头 / 三通 / 异径管 / 管箍 / 管帽 / 大小头 / 管座 / 封头 / 短节 / 管堵 |
| **阀门** | — | 阀门 / 球阀 / 闸阀 / 蝶阀 / 截止阀 / 止回阀 |
| **法兰** | — | 法兰 / FLANGE |
| **紧固件** | — | 螺栓 / 螺柱 / 螺母 / 紧固件 |
| **垫片** | — | 缠绕垫 / 垫片 |
| **支吊架** | 独立分类，不属于管件 | 吊架 / 支吊架 / 碟簧 / 弹簧支架 / 管道支架 |

**匹配顺序**：管件**优先于**管材（避免"无缝弯头"被"钢管/焊管"类词抢先匹配）。

## 数据安全红线

1. **代码中禁止出现任何业主单位名称**（如镇海炼化、安庆石化、中石化、中海石油等）
2. 制造厂家识别采用**纯标签驱动**：通过 `客户名称 / Customer / 项目名称 / Project Name / 采购单位 / 收货单位 / Sold To` 等**通用字段标签**拦截甲方信息，**不写死具体业主名**
3. 工具**从不读取、不保存、不输出**业主单位 / 项目名称字段；解析结果仅含产品、材质、规格、数量、炉批号、证书编号、制造厂家等**物资字段**
4. 新增演示数据 / 模板时，工程名称、领用单位、采购单位一律**留空**；制造厂家正常保留
5. 每次版本提交前跑一次敏感词扫描：

```bash
grep -n "镇海\|安庆\|中石化\|中国石油化工\|中海石油\|焦化\|四合一\|连续重整\|运行二部\|运行三部" 材料录入桥接工具_vX.X.html
```

> 测试 fixtures 保留原始 OCR 数据（是解析输入，不是代码），如需彻底脱敏另行处理。

## 版本迭代标准流程

```
1. 从 main 切分支        git checkout -b feat-vX.X-<主题> main
2. 复制新版 HTML         cp 材料录入桥接工具_vX.X.html 材料录入桥接工具_vX.X+1.html
3. 改代码                遵守三条铁律
4. 测试脚本指向新版      sed -i "s/_vX.X.html/_vX.X+1.html/" test_v74_json.js
5. 跑回归                node test_v74_json.js   ← 铁律一，必须全绿
6. 新增序号同步三处      规则Excel + classifyProduct + 测试断言   ← 铁律三
7. 更新文档              CHANGELOG.md（修复/新增/测试结果）、README.md（版本说明）
8. 敏感词扫描            见上方第 5 条
9. 提交到 feat 分支      git add -A && git commit -m "..."
10. 推送                 git push -u origin feat-vX.X-<主题>
```

## 环境注意事项

- **分支名不要用斜杠**：本环境 `.git/refs/heads/` 下带斜杠的子目录 ref（如 `feat/v7.7-xxx`）写入不持久，`checkout -b` 会静默失败 → **统一用连字符**（`feat-v7.7-xxx`）
- **`git reset --hard` 会清掉未跟踪文件**：包括 `tests/fixtures/` 里的新 JSON 和测试数据。误删后可从 dangling commit 恢复：
  ```bash
  git fsck --lost-found          # 找悬挂提交
  git show <hash>:<path> > <path>
  ```
- **提交前确认分支**：`git rev-parse --abbrev-ref HEAD`，避免改动误落到 main
- **GitHub 推送**：本机走 7890 端口代理（`git config --global http.proxy http://127.0.0.1:7890`）；首次 push 需交互式登录，自动化环境无法完成，需手动执行

## 附：事故复盘（V7.7 序号29）

### 现象
序号29（亮亮）11 页 JSON，工具只解析出 10 条；第 6-10 条规格型号/炉号/批号为空；第 2-5 条"无缝弯头90°/无缝三通"被判为**管材**。

### 关键实验：与 V7.7 脱敏无关
用 **V7.6（未脱敏原版）** 直接跑序号29，复现**完全相同**的错误（同样 10 条、同样字段错位、同样分类误判）。

→ 证明这是 **V7.6 就存在的潜伏 bug**，V7.7 脱敏只改了 `detectCompany` 过滤正则，出错的 `parseHengtongCert` / `classifyProduct` 一行未动。

### 两个潜伏 bug

| bug | 位置 | V7.6 为何没暴露 | 序号29 如何触发 |
|---|---|---|---|
| 检测条件只查前 5 行 | `parseHengtongCert`: `table.slice(0,5)` 找"供货状态" | 序号26 表格"供货状态"恰好在前 5 行内 | 部分页面首行多"收货单位"，"供货状态"被挤出前 5 行 → 检测失败 → 漏 1 条 + 字段错位 |
| "无缝"误判为管材 | `classifyProduct`: `/钢管\|无缝\|焊管/` | 以前没有带"无缝"前缀的**管件**名 | "无缝弯头90°/无缝三通"被"无缝"匹配 → 错判管材 |

### 根因总结
解析器检测条件**假设太脆弱**（"供货状态必在前 5 行"），分类规则**太宽泛**（用工艺词"无缝"当品类依据）。V7.6 的测试样本恰好都躲过了，序号29 一次性引爆。

### 修复
1. `parseHengtongCert` 检测拼接改为全表扫描
2. `classifyProduct` 管件优先于管材，移除管材识别词中的"无缝"
3. 修复后：11 条全部正确，回归 16 通过 / 9 既有偏差 / 0 错误

### 教训
**"这个版本很稳定"只对已测数据成立。** 新数据变体是照妖镜——所以铁律一（先测试再交付）是唯一能拦住这类 bug 的手段。
